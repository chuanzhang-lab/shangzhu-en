# i18n 架构整改计划 V3（shangzhu-en）

> 由 `code-improvement-plan` 技能产出。范围：**文案层与其边界**（`src/i18n/`、
> 引擎里的语言常量、数据文件里的展示文案、以及守卫策略）。
> 结论均来自**实测**，不是推演。

## 1. 背景与目标

- **项目**：本地优先财务建模工作台。**本仓是英文版部署**（`SHANGZHU_LOCALE=en`），
  同时保留中文语言包（双仓中的英文仓）。
- **i18n 的定位**：输出层展示文案的唯一出处，部署级 profile，不做运行时切换。
- **本次目标**：把 i18n 从「后天 retrofit + 人工白名单硬撑」改为
  「**结构性不可能漏**」：
  1. 英文部署下**真实渲染输出**不含中文（端到端可验证，不靠自觉）；
  2. 展示文案不再藏在数据文件与引擎常量里（数据面 / 展示面分离）；
  3. 守卫从「只查已登记模块」反转为「默认全查 + 例外登记」。
- **范围总述**：加 1 条端到端守卫 + 修 3 类泄漏源 + 反转守卫策略。

## 2. 现状总结

### 2.1 资源层其实是干净的

| 指标 | 实测 |
|---|---|
| i18n 键数 | en **1106** / zh **1106**，en 独有 0、zh 独有 0（奇偶完全对等） |
| `en.yaml` 值里含中文的键 | **0** |
| 回退链 | 当前 locale → en → `[i18n:missing:key]` + ERROR 日志（不静默空串） |

所以「两套 yaml 靠奇偶校验硬撑」这个判断**只对了一半**：资源层本身是齐的，
真正漏的是**资源层之外**。

### 2.2 真正的泄漏（实测）

英文部署下跑一次 `quick_scan`，输出里的中文片段：

| 场景 | 泄漏片段 |
|---|---|
| 未识别行业（走 fallback 模板） | `无限`×4、`无数据`×2、`其他`、`未知`、`建议提供更多项目细节以获得更准确分析` |
| 已识别行业 = 餐饮 | `杯`、`个月`、`新店前 3 个月客流通常只有目标值的…`、`无限`、`餐饮` |

**即：英文版会输出整句中文。** 而当时测试 611 条全绿。

### 2.3 核心结论

1. **没有任何一条断言检查「真实渲染输出不含中文」** —— 这是 9+ 处泄漏
   在 611 条测试全绿下存活的直接原因。
2. **展示文案住在数据文件里**：`config/industry_templates.yaml` 有 **53 处中文
   展示值**（12 个行业的 benchmark + fallback 兜底），英文部署原样吐给用户。
3. **引擎用中文字符串当协议常量**：`_ENGINE_INFINITE_MARK = "无限"` 参与
   `== "无限"` 比较，渲染层要做映射但映射不全。
4. **i18n 改造靠人工白名单**：`CONVERTED_MODULES` 只登记 4 个模块
   （op_executor / advisor_formatter / param_guard / param_advisor），
   而泄漏发生在未登记的 `financial_calculator` / `formatter` / `workflow_engine` /
   `decision_engine` / `report_generator`。
5. 代码中含中文的字面量共 **187 个**（已排除 docstring）：约 59 个是
   **数据键/匹配规则**（不该翻译），约 **128 个疑似展示文案**（应外置）。

## 3. 问题清单

| 编号 | 严重度 | 现象 | 位置 | 影响 |
|------|--------|------|------|------|
| I-01 | **严重** | 英文部署渲染输出含中文（9+ 处，含整句） | 全链路；无端到端守卫 | 英文产品露中文，直接击穿英文版定位 |
| I-02 | **严重** | 53 处中文展示文案存在**数据文件**里，英文版原样输出 | `config/industry_templates.yaml` → `benchmark.*`（12 行业 + fallback） | 数据面/展示面未分离；改英文要动共享数据文件，会波及中文版 |
| I-03 | **严重** | `_ENGINE_INFINITE_MARK = "无限"` 用中文串当协议常量 | `financial_calculator` / `formatter` / `workflow_engine` / `decision_engine` / `report_generator` | 语义与展示耦合；漏一处映射就露中文 |
| I-04 | **一般** | 守卫只查 `CONVERTED_MODULES`（4/~29 模块） | `tests/test_i18n_guard.py` | 未登记模块写死中文不会被抓；新代码天然无覆盖 |
| I-05 | 轻微 | industry 数据键（`餐饮`）出现在英文输出 | workflow_engine 来源串 | 同 `industry_name()` 已解决的问题，另一条路径没走映射 |

严重度定义：致命=无法运行/数据丢失；严重=核心功能错误；一般=可维护性/覆盖缺陷；轻微=风格。

## 4. 改进范围与目标

**要改**

| 项 | 完成标准 |
|---|---|
| I-01 | 新增端到端守卫：英文部署下 `quick_scan` 全字段输出断言无 CJK；并把已知泄漏钉成清单 |
| I-02 | 展示文案从 `industry_templates.yaml` 迁到 i18n（或提供 en 侧展示值），数据文件只留数值键；中文侧输出逐字不变 |
| I-03 | `"无限"` 协议常量改为语言无关（常量/哨兵值），渲染层统一走 `t()` 映射 |
| I-04 | 守卫反转：默认扫描**全部** `src/**/*.py`，例外用白名单登记（新模块自动被覆盖） |
| I-05 | 来源串里的行业键走 `industry_name()` |

**不做（范围外）**

- 不做运行时 UI 切换（部署级 profile 是既定设计）；
- 不改 `src/i18n/zh.yaml` 的**值**（中文侧零改动是硬约束）；
- 不合并中英双仓（那是仓库治理决策，不在代码层）；
- 不翻译 `rules/zh.yaml` 的输入解析规则（「元」「万」是中文输入语法）；
- 不翻译引擎里的**数据键**（餐饮/SaaS…）——只做展示名映射。

## 5. 项目边界声明

- **范围内**：`src/i18n/{en,zh}.yaml`、`src/**/*.py`、`config/industry_templates.yaml`、
  `tests/test_i18n_guard.py`、`docs/PLAN_I18N_ARCHITECTURE_V3.md`。
- **范围外**：另一仓库 `chuanzhang-lab/shangzhu`、`src/web_static/*`（前端已走 `/i18n.js`）、

## 6. 改进设计（十维度）

| 维度 | 设计 | 落点 | 验收 |
|---|---|---|---|
| 架构 | 三层分离：**数据键**（不动）/ **展示文案**（i18n）/ **协议常量**（语言无关） | 全局 | 无中文串参与 `==` 比较 |
| 功能 | 英文部署输出零 CJK；benchmark 展示走 i18n | formatter / workflow_engine | 端到端断言 |
| 数据 | `industry_templates.yaml` 的 `benchmark` 只留**数值**键（`*_min/max` 等）；文案键迁 i18n，缺失时回退空而不回退中文 | config + i18n | 中文侧输出不变 |
| 接口 | `t()` / `industry_name()` 签名不变；新增 `bench_text()` 之类的展示映射函数保持只读 | `src/tools/` | 无破坏性变更 |
| 性能 | 文案仍在进程内缓存；新增映射不得每次读盘 | i18n | 无新增 IO |
| 安全 | 不改输入校验与密钥路径 | — | — |
| 可维护性 | 例外白名单集中登记、每条写原因（否则后人只会往里加） | `test_i18n_guard.py` | 白名单条目带注释 |
| 可靠性 | 映射缺失时按「缺失不冒充」：宁可显示 `—` 或省略该行，**绝不回退中文** | 渲染层 | 断言兜住 |
| 可测试性 | 端到端 CJK 守卫 + 反转后的全量源码扫描 | tests | 回退改动 → 转红 |
| 兼容部署 | 中文侧输出逐字不变；单点提交可 revert | git | `git revert` 可回 |

### 6.1 关键设计：缺失时**绝不回退中文**

现在「映射缺失 → 回退数据文件里的中文值」是漏的根源。改为：

```python
# 渲染 benchmark 文案
text = t(f"bench.{industry}.key_warning")     # 走 i18n
if text.startswith("[i18n:missing:"):
    return ""            # 宁可省略该行，也不回退中文数据值
```

这与项目既有哲学一致：**缺失不冒充**。

- **顺序**：N-01 → N-02 → N-03 → N-04 → N-05 → N-06
- **里程碑**

## 9. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| 改 `"无限"` 常量会让断言 `== "无限"` 的中文测试转红 | 高：中文测试是「引擎行为未变」的 oracle | 改常量即**行为变更**，须同步更新那些断言并说明；若争议大则改为「渲染层映射补全」的保守方案 |
| benchmark 文案外置要动共享数据文件 | 中：可能影响中文版 | 数据文件只删/留数值键，文案值同时补进 zh.yaml（中文输出逐字不变有测试兜底） |
| 守卫反转后一次性爆出上百处 | 中：一次修不完 | 分批：先白名单登记「已知且合法」的数据类字面量，再逐个清理展示类 |
| 端到端守卫可能漏掉未覆盖的输出路径 | 中 | 守卫覆盖 `quick_scan` + `/chat` 两条真实路径；后续每发现新路径补一条 |

## 10. 验收标准

- **总体**：`pytest tests` 全绿；英文部署下 `quick_scan` 与 `/chat` 输出**零 CJK**。
- **N-01**：守卫存在且对已知泄漏敏感（回退任何修复 → 转红）。
- **N-02**：英文输出无 `无限`；中文输出仍「无限」。
- **N-03**：英文输出无 benchmark 中文（杯/个月/新店前…）；中文 benchmark 逐字不变。
- **N-04**：`CONVERTED_MODULES` 白名单语义反转为「例外清单」，且条目带原因注释。
- **N-05**：英文输出无裸行业键 `餐饮`。

- **六维度**：错误纠正 / 逻辑修正 / 模块冲突 / 运行改进 / 功能边界 / 工程完整性。

## 12.2 过程中实测到的三个「想错的地方」

1. **`_rw_display(rw)` 是静默无效的**：`_calc_runway` 的产物是 **dict**，
   哨兵藏在 `rw["runway_months"]` 里。拿整个 dict 去 `== INFINITE_MARK`
   永远为假，映射不生效但也不报错 —— 加了 `_rw_display_dict` 透一层才真生效。
   （第一版改完守卫仍红，是这个原因。）
2. **`wf.common.infinite` 是多余的键**：`fmt.common.infinite` 两侧早就存在
   （zh `无限` / en `Unlimited`）。我先按 `wf.*` 命名空间新建了一个，等于
   造了第二个真值源 —— 已回退，统一用 `fmt.common.infinite`。
3. **反转扫描今天抓不到东西**：新纳入扫描的 7 个模块全是空 `__init__.py`。
   反转的价值在**默认方向**（漏登记 = 以后没人管 → 漏登记 = 现在就红），
   不在当下战果。真正的泄漏是端到端守卫抓到的，不是静态扫描抓到的。

| 维度 | 结论 | 证据 / 残留 |

## 12.5 中文侧 oracle（逐字比对，非推断）

| 场景 | 客流 | 利润率 | 回本 | 风险 |
|---|---|---|---|---|
| fallback | 未知 | 无数据 | 无数据 | 建议提供更多项目细节以获得更准确分析 |
| 餐饮 | 80-250 杯 | 15-25% | 6-12 个月 | 新店前 3 个月客流通常只有目标值的 40-50% |
| SaaS | 不适用（按 MRR 衡量） | 目标 20-30%（初期亏损正常） | 18-36 个月 | LTV/CAC 应 > 3，月 churn < 5% |

`zh.yaml` 本轮**只新增** 4 个 `bench.fallback.*` 键，既有值一处未改
（`git diff src/i18n/zh.yaml` 可核）。
